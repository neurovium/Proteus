# Meta-Model Comparison: v3 (NeuroGhost revision) vs. v4 (`proteus_meta_model_v4.yaml`)

Notes comparing meta-model v4 against Dorota's v3 revision, and recording where v4 also tightens our own v2. Lineage: v1 was the initial colleague draft; v2 was the PROTEUS redesign (see `meta_model_comparison.md` for that comparison); v3 is the revised model in `djarecka/NeuroGhost` (`schemas/meta_model.yaml`, branch `model_updates`), which implemented several of v2's ideas and added mechanisms of its own; v4 is the synthesis. The rule applied throughout: where v3's mechanisms are better engineering, v4 adopts them integrally; where v3's architecture diverges from what the alignment computation and the curation lifecycle require, v4 keeps the v2 architecture and says why.

## What v4 adopts from v3

These are not courtesy inclusions — each replaces or extends something v2 did less well.

- **HashSubset: the hash scope is now machine-readable.** This is the single biggest improvement in v3 and it becomes v4's identity mechanism. v2 stated the hash scope in prose ("definitional content only, provenance excluded") and trusted implementations to agree with the prose. v3 tags every identity-defining slot with `in_subset: HashSubset` and derives the hash field set from the schema's own metadata, so the identity contract is enforceable, diffable, and impossible to drift from silently. v4 keeps the mechanism and changes only the scope (below).

- **Hash-stability engineering.** Two failure modes v3 caught that v2 never articulated: an identity-participating boolean whose absence hashes differently from an explicit `false` (fixed with `ifabsent: 'false'` on `abstract`, `required`, `multivalued`, `is_hub`), and multivalued identity slots silently defaulting to null inside the hash computation (fixed by requiring explicit passing, with canonical ordering, enforced by the hash function). These are exactly the bugs that make content-addressed registries drift without anyone noticing. v4 adopts both, stated as design principle 6.

- **Quantity-kind unit modeling.** v3's `UnitOfMeasure` carries `has_quantity_kind` (the QUDT quantity-kind IRI), which lets incommensurable units be vetoed on dimension alone, before and independent of any conversion-factor lookup — plus `ucum_code`, `symbol`, and `abbreviation`. v4 merges this with v2's `qudt_unit` (the unit IRI itself, the direct key into QUDT dimension vectors and conversion factors), giving the unit veto a cheap first tier (quantity-kind mismatch) and a precise second tier (dimension vectors).

- **PROV-O naming throughout, including `had_primary_source`.** v2 used `pav:` terms for creation provenance; v3 used W3C PROV-O properly (`prov:wasAttributedTo`, `prov:generatedAtTime`, `prov:wasGeneratedBy`, `prov:wasDerivedFrom`) and modeled `prov:hadPrimarySource` as a real entity-to-entity link rather than a denormalized label. v4 retires the `pav:` slots and adopts the PROV-O names, and `had_primary_source` on `ProvenanceInfo` now records the exact `SourceSchemaVersion` whose ingestion first produced an entity — outside the hash, where provenance belongs.

- **Declared ontology IRIs as first-class alignment evidence.** v3 preserved the source schema's own `class_uri`/`slot_uri` verbatim as slots on the entity. v4 generalizes this into a single `declared_uri` on `RegistryEntity` — the primary input to the declared-semantics signal — with one change of scope discussed below (it enters the hash).

- **Smaller adoptions, all correct:** `abstract` on `RegistryClass` (v2 had no way to record that a source declared a class abstract); `label` as a short identifier on `SourceSchema` (convenient for filenames, prefixes, CLI arguments); `mime_type` on schema versions; `confidence` explicitly optional, with the rationale that a manually declared mapping may carry no numeric score — and a missing confidence is missing, not zero.

## Where v4 overrules v3, and why

1. **Merge-by-hash is replaced by schema-anchored identity.** This is the architectural divergence and everything else follows from it. v3 merges entities across sources: identical name/description/range/unit hash to one node, with a `ProvenanceEntry` accumulating per attesting source, and aliases/`slot_uri` were excluded from the hash precisely to let this collapse happen. The problem is that the collapse converts an epistemic claim ("these two sources mean the same thing") into structural identity: an implicit exactMatch at confidence 1.0 that appears in no SSSOM output, carries no justification, cannot be reviewed, and cannot be retracted — the merged pair silently disappears from the alignment problem. The mechanism also contradicts itself: `ProvenanceEntry.source_description` exists to hold a source's differing description, but `description` is in v3's HashSubset, so entities with differing descriptions can never merge and the slot can never be populated. And when two merging sources declare different `slot_uri`s, the single-valued out-of-hash slot silently drops one — corrupting the declared-semantics evidence. v4's fix is one machine-checkable line: `defined_in_schema` is in HashSubset. Identical content in two different schemas is two entities; every correspondence, including the byte-identical ones, is an auditable `Mapping` record.

2. **The mapping layer returns to SSSOM.** v3's `Mapping` has a `target` but no `subject_id` — the subject is implied by the owning entity, because mappings are embedded via `skos_mappings`. There is no `MappingSet`, so one matcher run has no set-level provenance and cannot be superseded wholesale. `mapping_justification` is a free string ("manual", "exact_class_uri") rather than semapv, which collapses the distinction between statistical evidence and declared semantics that the pipeline preserves all the way to the provenance record (invariant 3 in `CLAUDE.md`), and there is no `author_id`, `reviewer_id`, `mapping_date`, or subject/object label denormalization — so an ACCEPTED status has no accountable reviewer and the review UI has nothing to display. None of it round-trips through `sssom-py`. v4 restores the full v2 mapping layer: standalone records with explicit `subject_id`, semapv justification enum, curation attribution, and `MappingSet` as the unit of a pipeline run.

3. **Version anchoring is rebuilt rather than removed.** v3 has two version mechanisms and its own comments condemn both: `SchemaSource.source_version` is frozen at first ingestion and never updated, and `SchemaVersionSnapshot` is write-only, mints a self-invented semver that ignores the source's real declared version, and is flagged as a removal candidate. Removing the snapshot without a replacement would leave no versioning at all beyond `derived_from` lineage — no "these entities came from release 2.1 specifically", no named graph per version, no reproducible statement of which versions an alignment run compared. v4's `SourceSchemaVersion` is immutable, carries the source's own `version_label` verbatim (never bumped by the registry), an `artifact_hash` that makes re-ingestion idempotence a checksum comparison rather than stored history, `prior_version` lineage, and an entity manifest (below).

4. **`source_native_id` is restored.** The verbatim source identifier (the raw column name `z_spec`) is what lexical blocking and matching operate on, and v3 has no home for it — in a merged-entity design it would belong per-source on `ProvenanceEntry`, which doesn't carry it. In v4 it is a hash-scoped slot on the entity, preserved exactly.

5. **`value_type` is a `uriorcurie` again.** v3 typed `range` as a plain string holding primitive type *names*, which reintroduces the "float" vs "xsd:float" vs "double" ambiguity across sources. Datatype compatibility is an alignment signal and incompatibility a veto, so the value space must be canonical: an XSD CURIE or a ValueSet hash_id, with ingestion responsible for normalizing source-native type names.

6. **`SlotAssignment` instead of the `Rule` stub.** To be fair to v3: parking requiredness and cardinality on a separate `Rule` is *coherent* under merging — the same merged property genuinely can be required in one source's usage and optional in another's. But under per-source entities that situation is two entities connected by a Mapping, class-local constraints become definitional content again, and `Rule`'s job ceases to exist — which is convenient, because v3's `Rule` is a stub with only name and description, so constraints were unrepresentable anyway. v4 restores `SlotAssignment`, whose constraint set is class-matching evidence (property overlap weighted by requiredness and cardinality).

7. **`Relation` is restored.** v3 removed it as "present in the schema, never actually needed" — true for its local use, but definitional relations (Detector isPartOf Instrument) populate the neighborhood graph that the structural channel's personalized-PageRank diffusion propagates over. Removing them thins the product graph and weakens the one signal designed to catch matches that share no vocabulary.

8. **`EQUIVALENT_CLASS` is restored to the predicate enum.** v3's mapping enum stops at the SKOS graded vocabulary. Without `owl:equivalentClass`, the Stage 5 logical-repair pass has no strict-equivalence predicate to translate, and no human-issued mapping can ever license reasoning. It remains exclusively human-issued and sparingly used.

## Where v4 tightens v2 (found while writing v4, not while reviewing v3)

- **The hash is schema-anchored but version-free — v2 never actually decided this.** v2's prose rule ("everything except provenance") reads naturally as including `defined_in`, the schema *version*. But if the version is hashed, an element unchanged between two versions of the same schema gets a new hash_id on re-registration — which directly contradicts the property v2's own comparison document promises ("unchanged elements keep their identities and accepted mappings, and only what changed re-enters the matching queue") and which Stage 6 idempotence depends on. And if neither schema nor version is hashed, byte-identical content across two *different* schemas collides — v3's merge bug at lower probability. v4 resolves the trilemma explicitly: the schema's stable identity (`defined_in_schema`) is in the hash, the version is not, and version membership lives in `SourceSchemaVersion.entities` — a manifest of hash_ids per version. Cross-version diff is manifest set-difference; re-registration never touches unchanged entities; anti-merge holds across schemas. This was a latent ambiguity in v2, not a cosmetic one, and v3's HashSubset mechanism is what forced it into the open — declaring the scope precisely made the contradiction visible.

- **Aliases are in the hash, and the consequence is accepted deliberately.** v3 excluded aliases from identity solely so cross-source entities could collapse; with that motivation gone, source-supplied synonyms are definitional content and belong in scope. The trade-off: a source that only adds a synonym in a new version mints a successor entity (new hash_id, `derived_from` the predecessor) that re-enters matching. This is intended — the lexical evidence changed, so re-matching is correct — and the write-back carries the predecessor's accepted mappings forward as fast-confirm proposals rather than losing them.

- Already listed above as v3 adoptions, but they change v2: PROV-O naming replaces `pav:`; the unit object merges both models' fields; `declared_uri`, `abstract`, `label`, and `mime_type` are new slots v2 lacked.

## Summary

v4 is v2's architecture running on v3's mechanisms. From v3 it takes the machine-readable hash scope, the hash-stability rules, the quantity-kind unit veto tier, and PROV-O provenance — each adopted integrally, not bolted on. Against v3 it insists on the two decisions the alignment computation cannot function without: identity never crosses a schema boundary (all correspondence is an auditable SSSOM mapping, so nothing disappears from the alignment problem and nothing escapes review), and the mapping layer is standards-conformant end to end (explicit subjects, semapv justifications, mapping sets as reproducible run artifacts, accountable curation). And the exercise improved v2 itself: making the hash scope declarative exposed that v2 had never resolved whether the schema version participates in identity — v4 resolves it as schema-in, version-out, with version membership as a manifest, which is what preserves both the anti-merge guarantee and the monotone-growth property at once.
